# Progress — July 2026

Status snapshot of `rossaddison/ddd-template`: what's built, what's
deliberately out of scope, and how to pick further work back up.

## What this repo is

A lean Yii3 starter, extracted from `rossaddison/invoice`, meant to carry
only the reusable skeleton (auth, 2FA, RBAC, OAuth social login, a bare
Shell) plus one fully worked **Domain / Application / Infrastructure /
Shell** DDD example (Settings + Telegram bot connectivity) — a pattern to
copy when adding your own modules, not another invoicing app.

## Done

The app is fully runnable end-to-end: signup → login → mandatory 2FA setup
for the first (admin) user → 2FA verify → Shell → logout, all verified live
against a real local MySQL database (schema synced via `BUILD_DATABASE`,
not migration files) — see "Live-verified" below for exactly what was
exercised.

- **Package selection resolved.** `composer install` succeeds clean.
  Notable decisions, in case they need revisiting:
  - `cycle/annotated` stays at `^4.6.0` (not downgraded) — this repo uses
    `rossaddison/yii-cycle-1: dev-master`, not the official
    `yiisoft/yii-cycle`, because the latter only publishes `1.0.0`, which
    pins `cycle/annotated ^3.5`.
  - `yiisoft/yii-auth-client: dev-master` (official package, no tagged
    release yet) is used for OAuth, in preference to the
    `rossaddison/yii-auth-client` fork. Its `getCurrentUserJsonArray()`
    signature is `(OAuthToken $token): array` — narrower than the fork's
    3-arg version (`$token, $httpClient, $requestFactory`); only
    `VKontakte::step8ObtainingUserDataArrayWithClientId()` still takes the
    extra HTTP client/request-factory args.
  - PHP constraint is `8.3 - 8.5`.
  - `chillerlan/php-qrcode: ^6.0.1` added for 2FA QR codes (live-verified —
    real QR renders, real TOTP codes generated by the app were successfully
    verified end-to-end).
- **Domain / Application / Infrastructure / Shell example** (Settings +
  Telegram): `src/Domain/{Setting,Telegram}`, `src/Application/{Setting,Telegram}`,
  `src/Infrastructure/Persistence/{Setting,Telegram}`,
  `src/Infrastructure/Telegram/PhptgTelegramGateway.php`, `src/Shell/*`,
  `resources/views/shell/*`, `config/common/routes/routes-shell.php`,
  `config/common/di/shell.php`.
- **Auth/OAuth/2FA — fully ported and live-verified**, adapted from invoice's
  `src/Auth/*` with these deliberate simplifications for a "no frills"
  template (none of this is upstream invoice behavior, all decided and
  documented during the port):
  - **No email-verification/admin-approval gate.** Invoice requires a
    click-through email link before a signed-up user is `active`, plus a
    separate manual admin-activation step. This template drops both: local
    signup and OAuth signup both create an **active** user immediately,
    assign a role, and log the user straight in. `User.active` still exists
    as a plain admin-togglable disable flag (nothing currently flips it
    off — that's a natural extension point).
  - **HMRC / GovUk / OpenBanking / OIDC dropped entirely** — UK-tax and
    fintech-specific, not part of a generic template. Kept OAuth providers:
    Facebook, GitHub, Google, LinkedIn, MicrosoftOnline, VKontakte, X,
    Yandex.
  - **OAuth "access-token" bookkeeping dropped** (`Oauth2::getAccessToken()`
    and friends) — it only existed to support the click-through
    confirmation flow above; with that gone it was pure dead weight.
  - **`getConfigSenderEmail()`/`getConfigAdminEmail()`/`mailerEnabled()`**
    (invoice's `SettingRepository` convenience methods, built on a heavy
    `HttpApplicationRunner` config-re-bootstrap hack) replaced by a small
    `App\Auth\MailerAddresses` value object, DI-wired in
    `config/common/di/mailer.php` straight from `params.php`'s `mailer` key.
    Email-sending in Forgot/Reset-password no longer gates on
    `email_send_method`/`mailerEnabled()` — it just tries to send.
  - **Roles are literal strings** via `App\Auth\Roles::ADMIN` (`shell-admin`)
    /`Roles::USER` (`user`), not `AppConstants`. First user to ever sign up
    (local or OAuth) gets `ADMIN`; everyone after gets `USER`.
  - `App\Auth\Permissions` (invoice's `view.inv`/`edit.payment`/etc.
    constants) was **not ported** — irrelevant to this template; `Shell\Permissions`
    already covers what Shell needs.
  - Two-factor auth is mandatory for `Roles::ADMIN` regardless of the
    `enable_tfa` setting (same rule as invoice) — this is exactly what got
    exercised in the live test below.
  - New `src/Auth/MailerAddresses.php`, `src/Auth/Roles.php`,
    `src/Widget/Button.php` (trimmed to just the two 2FA keypad buttons —
    invoice's version has ~15 more methods, all invoice-specific).
  - New `src/Controller/SiteController.php` + `resources/views/site/message.php`
    — one shared Bootstrap-alert view for every Auth redirect target
    (signupfailed, forgotalert, resetpasswordsuccess, etc.), replacing
    invoice's dozen near-duplicate view files that each depended on
    `CommonViewInjection`-supplied translation-string arrays this template
    doesn't have.
  - `resources/views/site/privacypolicy.php` / `termsofservice.php` —
    genuinely generic placeholder legal pages (explicitly marked as such in
    the page itself), since OAuth/payment provider app-registration
    dashboards commonly require these URLs to exist. Linked from the footer
    of `resources/views/layout/guest.php`.
- **`resources/messages/en/app.php`** created — trimmed down from invoice's
  ~3,100-line file to just the ~70 keys this repo's ported code actually
  references.
- **`resources/rbac/items.php`** — `shell-admin` (all 3 Shell permissions)
  and `user` (`access.shell` only) roles.
- **`config/common/routes/routes.php`** — Site + Auth + Signup routes, same
  rate-limiting shape as invoice (global + per-IP counters on
  login/signup/forgot/reset/change).
- **`config/common/di/cycle.php`** gained a `DataWriterInterface::class => EntityWriter::class`
  binding — invoice has this in `config/common/di/as4.php` (a
  Peppol/AS4-specific file that was correctly dropped), and its absence
  here wasn't caught until the live signup test hit a
  `DataWriterInterface` DI-resolution error. Worth remembering if another
  invoice `di/*.php` file gets dropped wholesale — check what generic
  bindings might be hitching a ride in it first.
- **`vendor/bin/psalm --no-cache` is clean across the whole repo**
  (`errorLevel="1"`, `findUnusedCode="true"`).
- **`vendor/bin/testo --suite=Unit` — 22/22 passing**, zero markers other
  than pass: `Tests/Testo/Domain/{Setting,Telegram}`,
  `Tests/Testo/Application/{Setting,Telegram}` (ported from invoice's
  `ddd-template-shell` branch, fully generic), plus new
  `Tests/Testo/Auth/Controller/AuthTfaHelperTest.php` covering the
  TOTP/backup-code validation logic.

## Infrastructure hardening — ported from `rossaddison/invoice`, July 2026

Two generic Yii3 improvements made in `invoice` today, ported here since
both are framework-level patterns rather than invoicing-domain features
(the actual Worker-allocation/bulk-copy invoice features built in that
same session were **not** ported — out of scope for this template by
design, see "What this repo is" above).

- **`CacheInterface` now binds to APCu instead of `FileCache`**
  (`config/common/di/cache.php`), wherever the `apcu` extension is
  loaded — guarded with `extension_loaded('apcu')` rather than assumed,
  since calling `apcu_fetch()` etc. without the extension is a hard fatal
  error, not a graceful miss. In-memory instead of file I/O for both real
  consumers: the FastRoute route-dispatch cache (only active when
  `config/environments/prod/params.php`'s `enableCache` is true) and
  `yiisoft/rate-limiter`'s `SimpleCacheStorage`.
  - **Real, non-obvious consequence**: `CacheClearCommand`
    (`src/Command/CacheClearCommand.php`) now also calls
    `apcu_clear_cache()`, but that call runs on the CLI — which PHP gives
    its own APCu memory pool, completely separate from the web server's
    workers, always, with no configuration that shares them. So
    `php yii cache/clear` **cannot** actually clear the cache a running
    web server is serving from once APCu is active; only a web
    server/PHP-FPM restart does. The command now prints an explicit
    warning to this effect rather than silently claiming success. Caught
    via a local smoke test (`php -r '...apcu_store()...'` from the CLI
    showed `apc.enable_cli=0` here, confirming the pool split) before
    shipping the overclaim.
- **`config/web/di/mailer-file.php`** — dev-only (`YII_ENV=dev`) override
  pointing `MailerInterface` at `yiisoft/mailer`'s `FileMailer` instead of
  the real `yiisoft/mailer-symfony` ESMTP transport. Every email this app
  sends (e.g. `ForgotPasswordController`'s reset-link email) gets written
  to `runtime/mail/*.eml` instead of actually being sent — open the
  newest file with any text editor and the link is right there, no real
  inbox needed to test an email-driven flow locally.
- `.env`/`.env.example`'s `YII_ENV` comment expanded to explain both of
  the above or point at this section.

## Live-verified (real MySQL, real `php yii serve`, real HTTP requests)

- Schema sync: `BUILD_DATABASE=true` created `identity`, `recovery_code`,
  `setting`, `token`, `user`, `yii_rbac_assignment` tables from entity
  annotations alone.
- Landing page (guest + logged-in nav states), footer legal links.
- Signup (first user) → `User.active=1`, `shell-admin` RBAC row written,
  correctly redirected into mandatory 2FA setup (not straight to Shell).
- 2FA setup: real QR code rendered (`chillerlan/php-qrcode`, SVG data URI),
  real TOTP code computed from the extracted secret via `spomky-labs/otphp`
  (the same library the app uses), submitted and accepted — `tfa_enabled=1`
  persisted.
- 2FA login verify: fresh TOTP code accepted, landed on `/shell/setting`.
- Second signup → `user` role (not `shell-admin`) — confirms the
  first-user-only-admin rule.
- Logout (CSRF-protected POST, session regenerated).
- `/change` (change password), `/forgotpassword`, `/shell/telegram` all
  return 200 with expected content.
- `/showSetup` visited directly (no prior login-flow session state) throws
  a `TypeError` — expected, matches invoice's own unguarded
  `findById()` — not something this port introduced or needs to fix.

**Not live-tested this pass** (needs real provider credentials/callback
URLs, or a real Telegram bot token): OAuth login end-to-end against a real
Facebook/Google/etc. app, Telegram bot connect/test-message/webhook.

## Deliberately out of scope

- Any UK-tax/fintech-specific auth (HMRC, GovUk, OpenBanking, OIDC) — see
  above.
- Admin ability to flip `User.active` off, or a "reactivate" flow — the
  field exists and is checked at login, but nothing in this repo's UI
  currently sets it to `false`. Natural next feature for whoever builds on
  this template.
- Per-user Telegram notifications via `User.telegram_chat_id` — the column
  exists (merged from invoice's `UserInv`) but nothing reads/writes it yet;
  `Domain\Telegram\BotConnection` only covers the single global bot.

## Resuming

The template is complete and runnable as shipped. Natural next steps for
someone building on it: wire real OAuth provider credentials into `.env`
and test a live callback; connect a real Telegram bot via the Shell UI;
add your own Domain/Application/Infrastructure/Shell module following the
Setting/Telegram example.
